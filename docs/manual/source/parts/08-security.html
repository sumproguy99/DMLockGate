LockGuard stacks several protections, so that if one fails, the next one catches it. Security people call this defence in depth.

Castle thinking: moat, wall, gate, guards, locked tower. A burglar has to beat all of them, not just one.

Device binding, in detail

When binding is on, each person (except Super and Security Administrators) gets one registered device. LockGuard recognises a device by a long random cookie it stores in that browser. Signing in elsewhere triggers device_registration_required: you need a one-time registration code from an administrator to move to a new phone.

A name tag the website sticks on your browser so it recognises it next time. You can't see it, and other websites can't read it. If you clear cookies or "website data" on your phone, LockGuard won't recognise it any more, and you'll need a new registration code. Same if you switch from Safari to Chrome.

Remote unlocking and its policy

The Super Administrator chooses one policy for unlocking from the app:

standard

Signed in + allowed = unlock. Simplest.

step_up (default)

Also re-confirm your password or code (valid ~10 minutes). Recommended.

location_required

Also needs a recent location report. Location-aware access isn't finished yet, so this currently refuses remote unlocks.

disabled

No remote unlocking at all. Locking still works.

The audit log

Every sign-in, lock command, permission change, export and setting change creates an audit record: who, what, which door or person, when, from which device and address, and whether it succeeded, was denied, or failed. Records are chained with fingerprints (hashes). The database protection script (scripts\protect-audit-log.ps1) can additionally stop the app's own database user from editing or deleting them.

pwsh -File scripts\protect-audit-log.ps1 These are critical alerts. The diary might not be recording, or might be editable. Fix them before anything else: run the protection script above, check the database is up and the disk isn't full, then run php artisan lockguard:audit-verify.

"Condition" alerts (lock offline, jammed, state not confirmed, low battery, integration down, audit protection) resolve themselves when the problem goes away. High and critical alerts are attached to an incident automatically, so they can't be forgotten.

How long alerts, incidents and notifications are kept

Every night at 3:30 LockGuard deletes finished records past their time. The defaults:

RecordKept forCounted from
Resolved alerts180 daysWhen it was resolved
Closed incidents, with their timeline and their alerts365 daysWhen it was closed
Read notifications90 daysWhen it arrived
Unread notifications365 daysWhen it arrived
Alert email log90 daysWhen it was sent
Open or acknowledged alerts and incidents that aren't closed are never deleted, and an alert stays as long as its incident does. The audit log isn't touched, so what happened is still on record after the alert is gone. Each cleanup writes one security.pruned row saying how many records went. Administrators see the current periods under Settings → Notifications → How long records are kept. To change one, set LOCKGUARD_RETENTION_* in the server's .env (0 keeps those records for ever); run php artisan lockguard:prune-security to clean up straight away.

Your privacy

  • Passwords are stored as one-way scrambles (hashes), never as plain text. Nobody can read yours, not even the Super Administrator.
  • Two-step sign-in keys and the email password are stored encrypted.
  • Location is only recorded at lock/unlock time or when an administrator asks while the app is open, is kept 30 days by default, and every view of it is audited.
  • The Eufy password lives only on the server (in the bridge). Phones never see it.

Each tap becomes an access request that moves through stages. The receipt under the lock card shows them as ticks.

StageWhat LockGuard saysPlain talk
received / authenticatingChecking your request."Who's there?"
authorized / queuedApproved. Sending to the lock."You're on the list."
submittedSent. Waiting for the lock to report its new state.The message is on its way to the door.
confirmed_successConfirmed by the lock.The bolt moved, and the lock says so.
deniedNot allowed.A rule said no. The reason is shown (see error codes).
failedThe command could not be delivered to the lock.It never got there. The door didn't change.
unknown_resultThe lock did not confirm in time. Check the door before trying again.Maybe it worked, maybe not. Look.
already_in_stateThe lock already reported that state just now. Nothing was sent.It's already locked, silly.
expiredThe request expired before it could be sent. Nothing was sent.Too slow; cancelled for safety.
cancelledCancelled. Nothing was sent to the lock.Called off.

Before any command is sent, LockGuard runs its checks in order: account active → device allowed → lock registered and commands on → permission → lock access → time window → remote-unlock policy → identity confirmed → location (if required) → lock not busy. The first "no" wins, and its reason is what you see.

If the result is unknown, the lock might have already moved. Pressing Unlock five more times won't help and will trip the "repeated lock requests" alarms. Check the door first. A TCP packet walks into a bar and says, "I'd like a beer." The bartender says, "You'd like a beer?" The packet says, "Yes, a beer." That's basically the lock confirming your command.
